## SEC-01 — rejected requests monopolize the shared POST window

**Medium; confirmed availability weakness.** Denial of service; high confidence. No deployed attack claimed. **Owner decision pending.**

### Evidence, bounded reproduction and impact

- `apps/backend/src/http/ingress.ts:36–57` shares one arrivals array across all POST callers/operations; four active/64 arrivals per minute. It records before media/compression/declared length (`83–99`) and before challenge/grant/schema admission.
- `http/app.ts:31–38` checks mutation Origin. Direct clients can supply the publicly known value; Origin is cross-site protection, not authentication.
- `apps/frontend/src/server/bridge.ts:128–155` checks route/method/origin/media/length/eight slots. It rejects text/plain itself, so the isolated reproduction does **not** claim the bridge forwards wrong media. A real bridge caller can send valid application/json with malformed JSON/body/proof, which consumes the same recorded backend window before admission.
- Existing `http/ingress.test.ts` verifies slots/release/64-arrival expiry. [Audit evidence](RTL-023/security-evidence.json) adds the failure-count reproduction using actual compiled middleware, fake time and EventEmitter objects. No sockets/provider calls/app mutation or hosted behavior.

64 wrong-media middleware attempts return 415, but consume arrivals; the next valid-media attempt returns 429. Advancing 60 seconds restores 200/next. Real source ordering similarly records valid-media malformed-body attempts before parser/admission failure. An attacker need not pass Turnstile to occupy the pre-admission window.

Repeated abuse can keep legitimate vision/Tailor/logo admission busy. Paid/native work remains bounded, no cross-visitor data changes and basic local store controls survive. This is fairness/availability, not an unlimited parser-memory finding, so severity is Medium. The cap is valuable; simply removing it is unsafe.

### Careful fix choices

**Start with** SEC-03's cheap public-ingress abuse controls before app CPU; preserve the global ceiling as emergency protection. Measure complete normal request rates before thresholds: 15 photos are one batch, not 15 admissions. Include challenge, uploads, chat, optional logos, deliberate retry and multiple ordinary visitors. Use existing generic `BUSY` behavior, no raw IP/content logging or automatic retry storm.

If desired audience still needs stronger fairness, approve a **small bounded refinement**: classify HMAC-valid already-issued safety sessions separately from unknown arrivals and reserve a measured amount of capacity for legitimate/initial admission, retaining a hard total active/body/native/paid ceiling. Verify the signature before trusting fairness; cookie shape, caller workspace/role or arbitrary forwarding headers are not identity. Unknown visitors still need finite CPU/map/key/window/slot limits. No login/database/fingerprint/queue by default; exact allocation requires measured traffic and feedback.

Moving cheap media/length checks before long-lived arrival recording is a narrow improvement only. It does **not** fix valid-media invalid-body abuse by itself. Do not raise/remove 64, refund every failed expensive request, move limiting after raster allocation, trust raw X-Forwarded-For, weaken challenges or suppress private failure logs. Owner may instead accept the explicit availability risk for a private/restricted demo; paid off alone does not remove this effect.

**Potential approved ownership:** ingress, existing safety/admission ownership only if necessary, focused ingress/admission/bridge tests and approved release ingress policy. No financial/session/style/model payload change or generic browser/server rate utility. Inert factories and public codes/status/copy remain unless a concrete approved change requires otherwise.

**Meaningful validation:** Abusive unknown caller cannot starve a distinct valid session within the agreed window; invalid signature cannot obtain protected allowance; legitimate initial admission works; hard total work/memory remains bounded; unknown-key flood cannot grow maps; window expiry/finish/close release exactly once; oversize/slow-body discard remains bounded. Offline tests deny paid/external networking. Normal complete multi-user walkthrough, cancellation/generic busy recovery, relevant phone/tablet/laptop evidence, applicable six gates and read-only execute/validate loop. Edge probes require approved resources; no production flood is authorized.

**Rollout/rollback:** Paid-off restricted staging first; compare sanitized aggregate rejection/latency/normal-flow evidence. Retain old hard-cap code rollback; on protection failure restrict exposure/keep paid off. Never weaken limits to make the demo appear responsive. Retain every old log and new finite diagnostics.

## SEC-03 — public traffic requires an origin-aware abuse policy

**Medium if publicly exposed; deployment policy gap, not a confirmed deployed vulnerability.** Denial of service/cloud-resource use. High confidence in source/runbook gap; hosted state unknown. **Owner decision pending.**

### Evidence and attack surface

`server/bridge.ts:64,154–155` limits eight simultaneous bridges, not all Next pages/static/RSC arrivals or a time-window rate. `http/ingress.ts:40` exempts GET health/config/FX from mutation limits. Currency `currency/service.ts:8–64` owns one refresh/cache/cooldown: a GET flood does **not** cause one FX-provider request per hit or OpenAI spend, but still consumes app/platform work.

`docs/operations/RELEASE.md:72–83` proposes ingress all for both initially IAM-private paid-off services, followed by separately approved frontend publication. No verified edge/rate/bot/origin-bypass policy exists for that step. Intended Cloudflare DNS/Turnstile is not proof that all primary/tag/custom URLs are protected. [Cloud Run ingress](https://docs.cloud.google.com/run/docs/securing/ingress) distinguishes direct internet access from load-balancer-restricted traffic; a proxied domain alone does not prove origin denial.

Preconditions: owner makes frontend public while managed `.run.app`, tags or another permitted URL bypass the chosen edge policy, or pages/GET/pre-admission traffic lacks agreed protection. A caller can consume work before challenge. Backend IAM must stay private; no public backend or unauthenticated provider dispatch is claimed.

Impact: degraded first impression/owner/customer views, CPU/request cost and shared bridge pressure, amplifying SEC-01. Correct max-instance settings and local eight/four/two slots limit some work, but are not edge DDoS guarantees. No limitless scaling claim or real deployed attack is made.

### Minimal deployment-focused options

Choose **one affordable approved strategy** before public sharing. Existing Cloudflare setup: narrow path-aware rate/bot rules, upload-safe limits and origin protection verified against managed URLs. Existing Google load balancer/Cloud Armor setup: restrictive frontend ingress can apply those controls to direct-origin traffic; cost/resources need explicit approval and are an option, not a required purchase for this demo. An explicitly private/restricted audience is also valid.

DNS proxy, Origin header or billing alert alone is insufficient. Enumerate actual primary/tag/custom URLs and health/operator exceptions; alternatives must reject or require intended protection. Preserve runtime audience → private backend flow. Blindly switching backend to internal-only can break it without networking setup. Do not log raw IP, trust arbitrary forwarded source headers, cache guest JSON/state or move private identity into browser code.

Preserve uploads/deadlines, smooth async state, sample/fonts/static/CSP/Next navigation/RSC/challenge and operator health. Calibrate to measured legitimate concurrent visits, not a tiny arbitrary threshold. Visitors retain generic busy/review recovery, with no hidden paid retry/login redesign/animation suppression/security prompt before the landing.
