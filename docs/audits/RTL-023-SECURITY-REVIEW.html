HIGH · IF PUBLIC PAID AI IS ENABLEDSEC-02

The spending allowance can refill with a new server.

Confirmed architecture property · Existing release condition · Not an active paid-off exploit

The threat

The current allowance belongs to each running backend. A restart, rollout or extra instance starts another allowance. “One server” does not guarantee one total spending ceiling.

Why it matters

If public visitors use funded AI without a verified external cutoff, total charges can exceed the amount we intended for the demo.

Selected fix

Keep paid AI off until an actual external cutoff and rollout policy are verified. A strict release record now requires recent evidence for this exact app and both images; a process allowance or email alert cannot open paid readiness.

Do not add a database by default, and do not mistake email budget alerts for an enforced cutoff.

How the fix preserves the demo

Photos, storefront styles, dashboard, wordmark and local controls remain usable. Keep all existing challenges, grants, limits and private logs. No cheaper interpretation, hidden retry or fake live fallback. Real spending checks need a separately approved account and budget.

Selected: paid stays off until real account refusal, restart/overlap and outstanding-cost evidence is supplied. The local gate is prepared; no account or cloud change has been made.

Medium priorities

MEDIUM · CONFIRMEDSEC-01

Rejected requests can make everyone else wait.

Availability weakness · Safely reproduced in memory · No internet or local-server flood

The threat

Previously all visitors shared one small request allowance. Requests that later fail can still fill it. One caller can make legitimate photo processing and Tailor requests receive “busy” for the rest of the minute.

Actual proof: 64 rejected attempts filled the window; the next valid attempt was busy. After a minute it worked again. Zero paid calls.

Selected fix

Reserve request capacity for genuinely issued sessions while keeping the hard total limit. Unknown callers cannot occupy all body handlers or the signed-session allowance; one issued session also cannot hold every handler. Public entry controls still protect first-time visitors.

Simply removing or increasing the limit is not the fix.

How the fix preserves the demo

Use the existing friendly busy response. Keep bounded upload/parsing/native/paid work, correct cancellation and every private log. Test full normal multi-visitor flows, including the sample, chat and optional logos, before settling thresholds. No login, fingerprinting or database is proposed.

The isolated proof used wrong media directly against middleware. The frontend already rejects wrong media; valid-media malformed bodies are the corresponding public path. No claim is made that the frontend forwards unsupported uploads.

Local fix: fairness and signature/expiry/cleanup regressions pass. Distributed abuse, initial-visitor capacity and hosted traffic still require the selected edge policy and normal-flow calibration.

MEDIUM · BEFORE PUBLIC SHARINGSEC-03

Protection must cover the direct URLs too.

Deployment policy gap · Actual cloud configuration is not available yet

The threat

Protecting only our custom domain can leave a direct Cloud Run URL or preview tag open to abuse. Pages and ordinary GET requests also consume server work before an AI challenge.

Why it matters

Traffic can slow the demo or raise cloud usage even when paid AI is off. Existing app limits protect expensive tasks, but do not prove edge DDoS protection.

Selected fix

A private server check now rejects requests that do not carry the trusted edge’s seal. It covers pages and assets while the API keeps its streaming upload path. Missing enabled settings fail safely. Actual edge rules and all URLs must be verified.

Use the existing Cloudflare proxy to overwrite the private header and apply measured traffic rules. No new load balancer, database or security-service purchase was made.

How the fix preserves the demo

Keep the backend private and preserve its caller identity. Maintain photos, fonts, navigation, challenge, long processing requests and operator health access. Do not impose a tiny arbitrary rate, suppress animations or cache private guest state. No hosted settings have been changed.

Local guard verified: direct page/asset/API requests are rejected, legitimate requests work and a full upload larger than 10 MiB passes without forwarding the seal. Actual cloud configuration and abuse-policy proof remain release gates.
