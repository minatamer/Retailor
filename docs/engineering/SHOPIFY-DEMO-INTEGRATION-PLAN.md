## Outcome and terminology

Retailor remains a clothing demo with a temporary browser-session storefront. A visitor may connect an eligible **Shopify test store** through Shopify's native consent screen, inspect its products, explicitly export selected Retailor garments as draft demo products, read the results back, update those exported drafts and remove them. The visitor supplies no API key or client secret. Retailor's operator configures one developer app on the server.

The Retailor preview is not a Shopify development store, a deployed Shopify theme or a permanent merchant backend. Connecting creates no products. Reading another store's products does not import them into Retailor's commerce graph, send them to AI or put them through Stripe. This first integration includes real catalogue read/create/update/delete experience without adding inventory adjustment, orders, customers, billing, publishing, themes or two-way synchronization.

The owner requested planning now and will finish the Shopify form later. Their subsequent local execution is authorized; native account use, tunnels, resource provisioning and publication need applicable authorization when reached. Missing credentials/distribution permission do not block independent local implementation and injected-provider checks. They do block claims that real OAuth, cleanup or outside visitors have been verified.

## Visitor experience

1. Keep photo intake, catalogue review and personalization. After accepting the first look, show an optional **Try Shopify with your test store** step before the storefront. Explain native consent, draft-only writes, data shared and automatic cleanup limitations. Offer **Connect Shopify** and an equally usable **Skip for now**. Skip opens the normal storefront/tour without an external account.
2. Connect navigates to the supported Shopify installation/authorization entry point. Shopify handles login/permission approval. Return to the same unexpired tab/workspace and the connection step; never restart catalogue generation or auto-export. Show the verified store name, connection state and **Continue to storefront**. Denial, unsupported distribution, missing configuration or interruption also offer Continue without Shopify.
3. Add **Connections** to the owner dashboard, after Personalize, using the existing responsive owner navigation. Use one Shopify card, not a generic integrations marketplace. A skipped visitor can connect here later; a connected visitor can inspect/refresh the catalogue, review/export selected Retailor products, update their exported drafts, remove selected owned drafts, or **Disconnect & remove demo products**.
4. A write review states destination store, selected garments, supported options/variants, prices in the shop currency, photos and draft status. Consent to OAuth and consent to sending products are separate. Each changed export requires a fresh explicit action; neither local edits nor restore silently write remotely. Read-back links open the exact Shopify admin product on the verified shop.
5. Show individual outcomes: created, updated, media processing, failed, outcome being checked, removal pending, removed or needs attention. Keep successful items visible after a partial failure. Never say disconnected/cleaned while removal is unknown. Shopify errors become useful fixed messages plus a request reference, without provider exception text.
6. Reset/expiry must remain available. Persist cleanup intent before detaching a connected workspace; a failed request does not strand the local reset behind an endless spinner. Server expiry is the backstop even if reset cannot reach the backend. Give a bounded explanation and manual cleanup instructions when access is revoked. Closing a tab is not a reliable immediate cleanup trigger.

Suggested plain copy: “Connect a Shopify test store to try reading products and sending draft demo products. We remove products created by this demo when you disconnect or the two-hour demo expires, while Shopify access remains available. Existing products are left alone.” Before exporting, explicitly explain that even edits made later in Shopify to these session-created products are removed during cleanup. Keep the longer provider-retention and access-revocation explanation behind an accessible information control.

If Shopify configuration is absent or the audience cannot install, keep Skip/Continue working and explain availability honestly. Do not show a pretend live success or ask visitors for private keys. An explicit development fixture may exercise the flow locally; it must be visibly simulated and unavailable as a public live fallback.

### Durable connection and cleanup ledger

This is an explicit expansion of the earlier “no durable application state” baseline: keep a small private integration ledger, not a hosted storefront or merchant database. It stores server session bindings/expiry, app/shop installation identity, encrypted access/refresh credentials and refresh version, OAuth attempt state, confirmed product/media IDs, export intent/revision/fingerprint, unknown outcomes and cleanup due/status. Do not persist original photos, catalogue descriptions, prompts or customer data in it. Temporary sanitized export photos have a separate short lifetime.

Define one storage interface with atomic compare-and-swap/leases. Supply an encrypted, crash-safe, ignored app-local persistent adapter for single-process local use and a private GCS generation-precondition adapter for restart/multiple-instance hosted use. Local mode must reject concurrent backend owners rather than pretend a filesystem is shared cloud storage. Reuse the existing GCS dependency and identity conventions, not checkout's process-scoped image namespace. No SQL/Redis service or general durable work queue is required.

**Do not put token/cleanup state in the current checkout-photo bucket without changing its approved storage design:** that bucket deletes objects after one day, and SDK encryption-at-rest alone is not application token encryption. Prepare a separate narrowly scoped integration bucket/prefix policy with application-encrypted credentials, finite retention and explicit identity/key rotation in the later operations guide. Actual bucket/IAM/key/scheduler creation needs separate authorization. Storage errors or absent encryption configuration disable connecting/writing; no volatile live fallback.

Reserve one installation lease per app/shop before token exchange. Initially allow only one active or unresolved workspace per shop; another browser gets a useful “already in use” response. Keep unresolved ownership/cleanup reservations until verified resolution or the explicit retention cutoff. Serialize refresh/exchange with durable fencing so new refresh tokens are committed atomically and late workers cannot overwrite them. Reauthentication must not lose an earlier cleanup ledger or let an old uninstall delivery revoke a newer installation. Lost refresh/exchange results require explicit reconciliation or reconnect, never guessed token reuse or hidden retry loops.

Read a bounded, paginated subset of Shopify products with escaped text, currency, supported option/variant summaries, draft/active status and validated Shopify media URLs. Existing merchant products are read-only. Show an empty catalogue, missing image and unsupported product cleanly; do not weaken Retailor's clothing/photo invariant or inject Shopify HTML. This packet does not import an arbitrary Shopify catalogue into the local graph. A later import feature would need its own mapping/recognition/financial plan.

Before each export, validate current Retailor clothing/product/photo records and review the frozen source revision. A non-USD test shop can be connected/read but export explains the mismatch and remains blocked. Do not create stock levels, inventory costs, tax/shipping rules or discounts by inference. Draft export is not a Shopify theme, publication, checkout or sale.

Persist a write intent and server-generated opaque export marker **before** each provider mutation, then persist exact returned IDs and read back status/variants/prices/media. Mark products with an app-owned per-session/export metafield and a human-readable Retailor demo label. A visible tag/title, caller-supplied ID or matching SKU alone never authorizes update/delete. Prove marker query/lookup behavior against the pinned schema. One local product maps to at most one session-created Shopify product. Duplicate clicks/restore/network retries reuse the same server intent. For a timed-out create, search/reconcile the server-held marker before any further create. Until conclusively settled, reserve its capacity and block conflicting actions. Unknown/partial variant or media work remains tracked and eligible for cleanup. ### Cleanup and connection states

Server state distinguishes `unavailable`, `disconnected`, `authorizing`, `connected`, `writing`, `checking_outcome`, `cleanup_pending`, `cleaning`, `cleaned`, `disconnecting` and `needs_attention`. UI may combine labels, but must not combine uncertainty with success. Keep installation/token state separate from per-session product/cleanup state.

On remove, disconnect, reset or server expiry: stop new writes; increment the generation; durably schedule cleanup; settle/reconcile in-flight writes; remove only this ledger's products/media; confirm known IDs deleted or conclusively already absent; then release temporary images and revoke access/uninstall if no unresolved ownership remains. Selected-product removal keeps the connection alive. For disconnect/reset/expiry with this single-session-per-shop policy, uninstall after all cleanup is confirmed, then erase credentials and close the connection. Retry uninstall separately if its result is unknown. If cleanup fails, retain protected access only for bounded cleanup and expose pending/needs-attention, never reuse it for writes.

An externally initiated Shopify uninstall, revoked permission, lost encryption key or provider outage can prevent remote deletion. Handle signed uninstall without trying to refresh a revoked token. Stop work, record unresolved product IDs and provide precise manual deletion guidance for those Retailor demo products. Do not claim Shopify automatically deletes them. Reconnect may reconcile the same ledger after verified shop ownership, within its retention window. Privacy redaction takes precedence over retaining recovery metadata; do not retain credentials indefinitely in the name of cleanup.

Run the same bounded cleanup service from a local backend timer/explicit CLI entry point, and from a **private scheduled invocation** in hosted operation. Prepare the command/entry point, authenticated invocation contract and deployment/IAM worksheet locally. An in-memory timer on scale-to-zero Cloud Run does not guarantee expiry cleanup. The hosted scheduler is a later resource decision/authorization and acceptance gate; no new public cron endpoint is allowed. The ledger is the only cleanup outbox, not a general background export/retry queue. Browser navigation/cancel can fence UI attachment but cannot recall a dispatched provider write; record its eventual/unknown ownership and clean it.
