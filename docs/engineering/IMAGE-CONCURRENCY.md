## Retailor’s current bottlenecks and semantic boundary

At the inspected `c4d22f6` baseline, `photos/sample.ts` fetched and checked fifteen release assets serially, and `PhotoController.add/recover` invoked one terminable browser image worker at a time before committing cache/selection/URL state. The RTL-003 follow-up now overlaps bounded browser work with ordered effects. No extra provider calls, keys, retry, budget, database, queue service or paid enablement is introduced. Three logos remain one optional n=3 batch; this is primarily the fifteen-product intake path.

## RTL-003 prioritized implementation allocation

1. Add a photo-specific ordered foreground pipeline: at most **two** work items live, each holding at most one result until its input-order commit. Avoid creating all worker promises up front. Attach failure handling immediately; partial invalid files become their own ordered issues, while good selections remain usable. Keep IDs, duplicate winner, selection order, notices, cache writes and progress deterministic when responses finish backwards.
2. Preserve pre-allocation count/original limits with reservations for pending source bytes/slots. If a second job cannot safely fit while an earlier result is unresolved, run the earlier job and reevaluate after its commit; do not reject a later valid item merely because a failed/duplicate earlier file temporarily reserved capacity. Recheck actual aggregate derivative/original bounds at commit. Two pending derivatives add at most 1.5 MiB transient encoded output; retained cache envelopes stay unchanged.
3. Use an independently bounded browser decode resource gate: at most **two actual workers**, with at most **24 megapixels total in active original decodes**. Each active worker retains its existing ten-second deadline/termination and current orientation/hash/metadata normalization. Queue waits and slots are foreground, bounded and cancelable, with no animation/user setting.

Scope pending work to the current controller generation and signal; cancel/reset/expiry/disposal terminate all active work, drop queued starts and never publish late URLs/cache metadata into a newer workspace. ## RTL-006 queued implementation allocation

After RTL-003 is implemented and cleanly validated, overlap two independent backend raster sanitizations through an injected inert **process-wide two-worker gate**, with at most two foreground waiters from the existing two request leases. Keep the manifest/hash/header checks before native allocation and the worker’s single-threaded Sharp/resource limits/deadline. Create a fresh worker per image; no retained cross-request image/parser pool.

Each request owns a bounded two-item pipeline. The shared gate caps actual CPU workers across two simultaneous paid requests, rather than accidentally multiplying to four workers. Fair FIFO release/cancel removes canceled waiters; capacity remains held until worker termination settles. A failed image aborts the request’s active siblings and prevents provider dispatch, then awaits cleanup before returning/releasing its request lease. Ordered output matches the approved manifest, actual sanitized-byte aggregate stays within 18 MiB, and incomplete/late batches cannot attach. No live-to-fake fallback or automatic retry.

Tests must inject blocked/reversed workers to prove two active/two waiting globally, no fifth native start, independent request cancellation, no released slot before termination, stable manifest order and zero provider dispatch on failure.
