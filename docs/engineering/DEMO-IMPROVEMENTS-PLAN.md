## 1. Standard GA4 with explicit commerce events

Use one **Standard GA4** Retailor property and one Web stream, with `gtag.js` through Next's existing script support. Google's normal Analytics offering is [free of charge](https://marketingplatform.google.com/about/analytics/). Normal browser tracking/reporting requires no Google Cloud billing account. Existing Cloud Run/storage costs remain separate. Exclude Analytics 360, BigQuery exports, Ads links, server-side tagging, Measurement Protocol, Data API dashboards and account-provisioning automation from this slice. No Google API key, service account or Analytics API secret belongs in Retailor.

### What Google supplies, and what Retailor must supply

After permitted tag initialization, GA4 supplies such automatic events as `first_visit`, `session_start` and `user_engagement`, plus browser/device/session context. Default page views and optional enhanced measurement can observe navigation, scrolling, outbound links, search, forms, downloads and supported embedded video; this does not understand Retailor's cart or verified Stripe outcome. See [event categories](https://developers.google.com/analytics/devguides/collection/ga4/events) and [enhanced measurement](https://support.google.com/analytics/answer/9216061?hl=en).

**Recommended settings:** enhanced measurement off, including history-based page changes; `send_page_view: false` on each initialization; manually send sanitized page views for committed navigation. Google's [manual page-view guidance](https://developers.google.com/analytics/devguides/collection/ga4/views) explains why automatic views must be disabled to avoid duplicates. Retailor's local MP4 is not the YouTube integration measured by enhanced video events.

| Event              | Send after this actual behavior                                                                                                                                                | Do not send for                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `page_view`        | Landing or an accepted logical workspace/store page becomes active; fixed safe location/title, one initial view after consent.                                                 | Every render, variant choice, pending route or failed/unmatched session. An unavailable page may have its own fixed page kind.              |
| `view_item`        | A valid, photo-backed product detail is displayed in shopper mode; once per product entry, including accepted Back/Forward navigation.                                         | Cards merely rendered in a grid, owner editing, hover, failed IDs or repeated effects.                                                      |
| `add_to_cart`      | Commerce accepts an addition or quantity increase; send the positive quantity delta.                                                                                           | Clicks rejected for stock, limits, photos, expiry or stale state.                                                                           |
| `remove_from_cart` | Commerce accepts a decrease/removal; send the removed quantity delta.                                                                                                          | A no-op quantity, failed mutation, purchased-bag clearing or reset.                                                                         |
| `begin_checkout`   | A valid bag first enters checkout review for that checkout intent. Reusing the same pending intent must not report again; a changed bag/new deliberate review is a new intent. | Merely opening the bag, invalid quote, availability probe, redirect retry or restore.                                                       |
| `purchase`         | Server-verified sandbox completion is accepted and `settleStripeOrder` successfully places the corresponding local order.                                                      | `checkout=success`, gateway creation, decline/cancel/timeout/stale return, simulated fallback orders or fictional seeded business activity. |

Use Google's [recommended ecommerce event shapes](https://developers.google.com/analytics/devguides/collection/ga4/ecommerce). `view_item_list`, `select_item` and `view_cart` are optional later conveniences; refunds and owner operations are outside this measurement slice.

### Payload and reporting policy

Every Retailor commerce event has fixed `demo_mode=portfolio`, `payment_mode=stripe_sandbox` or `local_simulation`, and `catalogue_source=sample|upload|mixed`. These are finite categories, never filenames or prompts. Production visitors are still using a demo: GA4 revenue means sandbox demonstration value, not business revenue. Do not import the dashboard's fictional sessions, reviews, buyers or sales into GA4. Development/tests send nothing to the real property; deliberate owner QA uses `debug_mode` and the developer-traffic filter in **Testing** before any permanent exclusion. Do not mark ordinary portfolio visitors as developer traffic.

Allow only numeric prices/quantities, USD/EUR, opaque generated product/variant IDs, finite category labels and fixed page/event categories. Use category-derived item labels such as `Demo jeans`; omit editable titles, brand/store names, sizes/colours/SKUs entered by visitors, descriptions, reviews, chat, photos, source hashes, filenames, image/signed/Blob URLs, email/contact/payment details, credentials, grants, Retailor security/session cookies and workspace IDs. No `user_id` or custom fingerprinting. Google's own consented pseudonymous browser/session identifiers remain part of normal GA4 collection. An opaque local order ID, prefixed `sandbox_`, can identify a transaction without exposing a Stripe Session ID.

Money comes from the existing accepted quote/order display snapshot, using integer cents until serialization. For purchases, GA4 `value` is discounted merchandise, excluding separately reported shipping/tax; its items must reconcile to that value and the captured verified currency/total. Reuse the existing USD/EUR allocation and residual rules; test THREAD10, multiple quantities and rounding. If a line's cent allocation needs splitting, use bounded item rows that preserve the exact total, not new price arithmetic. GA4's schema is a projection, never financial authority.

Prevent duplicates at the existing success boundary, outside rendering effects. Use one stable nonempty `transaction_id` per settled attempt, and a bounded local dispatch marker associated with the existing completed-checkout mapping, persisted in the same session projection. Mark the dispatch attempt before calling the optional sink; no replay after reload, Back/Forward, remount, restore, consent changes or duplicate return. Reset/expiry retires this state with its workspace. [Google also deduplicates purchases with matching transaction IDs](https://support.google.com/analytics/answer/12313109?hl=en); this is a second safeguard, not an exactly-once delivery guarantee. Browser blocking, storage failure and network loss can undercount. No retry queue, offline backlog, webhook or database is justified for demo analytics. Never replay events that happened before consent.

### Consent, URLs and external storage

Recommend **basic consent mode globally**: equal, accessible Accept analytics / Reject choices; shopping works before either choice. No Google tag download, collection, cookies or cookieless pings before opt-in. All advertising consent stays denied. A single versioned local preference records choice/time, expires after180 days and requires a new choice after a policy-version change; storage failure remains usable and fails closed after reload. Configure GA cookies as browser-session cookies (`cookie_expires: 0`), rather than the default long expiry; this can reduce repeat-visitor continuity and is appropriate for the demo. Provide a persistent Analytics settings control. On withdrawal, stop collection immediately, disable the loaded tag, clear Retailor's GA cookies and discard pending events. Consent is separate from the demo workspace; resetting a store must not silently grant analytics. Google's [basic consent implementation](https://developers.google.com/tag-platform/security/guides/consent?consentmode=basic) supplies the technical sequence.

Store names can include personal information. Both the raw slug in a pathname and the page title/referrer can disclose it. Before **any** tag initialization or event, set only fixed synthetic locations such as `https://tryretailor.com/store/product` and titles such as `Retailor demo product`; use an empty or fixed sanitized referrer. Maintain safe values across history changes and automatic engagement events, not only manually sent views. Strip query/hash entirely, including checkout attempts, search and arbitrary `utm_*`/click IDs; override campaign fields with fixed safe values instead of accepting free text. Retain `Referrer-Policy: no-referrer`. Test actual outgoing requests from first load, direct entry, consent, renamed routes and Stripe return; a filter in GA4 reports is too late. Query/email redaction is defense in depth and does not sanitize arbitrary store-name paths. See Google's [PII rules](https://support.google.com/analytics/answer/6366371?hl=en) and [configuration fields](https://developers.google.com/analytics/devguides/collection/ga4/reference/config).

GA4 stores permitted events and pseudonymous browsing context **externally at Google**. The two-hour local workspace lifetime/reset does not erase analytics already sent. Publish a concise privacy explanation of Google as recipient, purposes, consent/cookies, external handling/retention, withdrawal and owner contact. Recommend two-month event/user retention and no reset-on-new-activity extension; this setting does not delete standard aggregate reports on the same schedule. See [retention scope](https://support.google.com/analytics/answer/7667196?hl=en). Review the applicable [Google consent policy](https://www.google.com/about/company/user-consent-policy/) and audience obligations before enabling collection; consent mode alone is not a complete privacy notice or compliance decision.

The current CSP blocks Google endpoints. Add only the documented **non-Ads** Google tag/Analytics sources needed by the chosen configuration, based on Google's [CSP guide](https://developers.google.com/tag-platform/security/guides/csp). Keep Turnstile, the private origin guard, upload streaming and all existing controls intact; no wildcard-all scripts/connections or `unsafe-eval` in production. Verify regional collection works without adding advertising endpoints. Blocked scripts, missing/invalid ID, denial, timeout or adapter exceptions must never affect shopping, navigation, order settlement or private diagnostics. Analytics receives no technical exception/log payloads.

## 2. Readable addresses inside one temporary local session

Suggested paths:

| Path                                      | Local behavior                                                                       |
| ----------------------------------------- | ------------------------------------------------------------------------------------ |
| `/demo`                                   | Existing photo/review/personalize/owner flow and fixed Stripe return endpoint.       |
| `/demostore`                              | Home of the eligible local store with that exact active slug.                        |
| `/demostore/collection`                   | Existing collection view; filters/search remain local, not URL free text.            |
| `/demostore/products/<opaque-product-id>` | Existing product view; validate ID belongs to the current store and is not archived. |

Do not add per-product title slugs, separate collection entities or owner SEO editors just to fill these paths. Reuse `Storefront`, `BrowseState`, Tailor's product navigation, bag and the same `SessionController`. A small route adapter translates accepted URL navigation into existing controller transitions and projects accepted state back into history. It is not a second state store. Avoid keying a provider by slug/path; preserve one mounted owner for transitions and fence/dispose it on actual exit. Full reload uses existing strict restore.

**Slug policy:** normalize an accepted name to lowercase ASCII words separated by single hyphens, trim, cap at 48 characters; use `store` when no usable characters remain. Deterministic fallback `-store` handles reserved names, with the base truncated to keep the cap. Reserve all fixed top-level paths, including `demo`, `design`, `api`, `_next`, `privacy`, `robots.txt`, `sitemap.xml`, manifest/icon assets and any newly introduced fixed route. Reject encoded separators, dot segments, malformed escapes and excessive path depth/length before route interpretation. No redirects to caller-supplied URLs. There is one local active store, so no global name registry or availability check is needed. Identical names in independent sessions are independent stores, never a lookup of someone else's store.

Persist the current slug in a narrow optional/default-compatible projection field bound to the existing workspace identity/expiry. Allocate it on first accepted look; migrate an eligible older session locally without recognition or a provider request. Changing a draft name does not change the URL. Accepting a renamed look replaces the active slug and current history entry; the old slug then displays unavailable. Keep no permanent alias/tombstone service. Renaming to the same normalized slug leaves it stable. Reset/expiry removes the binding; a later independently created same-name store is a new local store, never recovery of the old one.

**Match before display:** a store path can select only the eligible current workspace with an accepted look, exact slug and valid product membership. During restore show neutral loading, then either the matched store or the unavailable explanation; never flash an unrelated saved store. Refresh/direct entry in the same eligible session restores locally without drafting. Memory-only recovery cannot survive a reload and must say so. Invalid/missing products show a local product-unavailable state and an action to this session's collection. Back/Forward must validate again, including after rename/reset/expiry, and must respect existing dirty-design review rather than skipping it.

Opening the same URL in another device, browser, incognito context or fresh tab without a matching session shows: **“This temporary store isn't available in this demo session. Store addresses cannot restore someone else's store.”** Offer **Start your own demo** to `/demo`, not recovery by name, automatic sample loading or a model request. Do not scan IndexedDB for another workspace or bypass cache ownership locks. Existing same-browser tab duplication/cache-lease behavior remains subject to the lifecycle checks; a URL alone never transfers storage or photos. No share UI, copy-as-public-link control, hosted snapshot, server catalogue lookup or database.

Beside the address in both the store and owner/design surfaces, keep visible copy:

> Temporary store address. Available only in this browser’s demo session. This address cannot be shared. Resetting or clearing the session removes the store.

Expose the address as local navigation, with no “Share store” action. Keep the expiry duration clear in existing lifecycle information. Reset/expiry while a nested path is open must immediately clear its content/dialogs and show unavailable (or deliberately replace to fresh `/demo`); old history entries cannot redisplay it. Keep existing photo/cache cleanup and generation fences. Do not extend the original two-hour expiry on navigation/rename, and do not promise physical erasure from providers or previously saved files.

Stripe success/cancel URLs remain the backend's fixed `/demo?checkout=...&attempt=...`. Restore/verify there through the existing flow, remove return parameters, then project to the validated local store address. Returning to a missing/expired/reset session must not create a new store or order. Do not place a free-form return URL or store name into the backend redirect contract.
