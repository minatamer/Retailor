## Recommendation

Yes: use a real **Stripe-hosted Checkout Session in a sandbox**, with the visitor's chosen store name and actual cart contents. The visitor enters Stripe test payment details, completes a simulated payment, and returns to a Retailor demo confirmation. This demonstrates a real integration while moving no real money. Stripe documents sandbox isolation from banking/card networks and its test payment primitives. [Sandbox behavior](https://docs.stripe.com/testing-use-cases)

**Visitor-uploaded clothing is the baseline requirement for the first complete integration.** The checkout must work with their own photos, edited garment details and selected variants. The sample collection is an additional case; sample-only success does not satisfy this plan.

The first implementation should demonstrate the gateway and verified return only. Keep the current connected local order simulation available separately. Do not automatically call `placeReviewed()` or claim inventory/order fulfilment from the Stripe return. Linking verified Stripe payments to durable orders is a larger future scope; it is unnecessary for the owner's stated gateway demonstration.

## Proposed visitor flow

1. The existing bag shows the real garments, chosen size/colour, quantity, promo and total. Checkout offers **Try Stripe sandbox** with a concise test-payment explanation. Keep the existing local demo checkout reachable while the integration is optional.
2. On deliberate confirmation, prepare one immutable, bounded checkout attempt. Recompute the quote on the server using shared commerce rules; bind its identity, workspace, revision, cart, currency, total and selected photo witnesses. A browser-supplied final amount is insufficient validation. The catalogue remains user-authored demo data, not an authoritative production merchant database.
3. Create one sandbox Session with inline items, per-session branding, fixed return URLs and a stable idempotency key. Redirect the browser to the returned Stripe URL. A direct server-created URL redirect does not require a publishable browser key; this follows Stripe's hosted flow. [Hosted flow](https://docs.stripe.com/payments/accept-a-payment?payment-ui=checkout&ui=stripe-hosted)
4. Successful payment returns to a brief checking state, then **Sandbox payment complete — no real charge** only after server verification of ownership, `livemode: false`, completed/paid state, currency and exact amount. Do not return customer email/address/card fields to the app. Consume the attempt idempotently and remove temporary return parameters from browser history after recovery.
5. Cancel/back restores the same store and bag without placing an order. A failed payment stays retryable in Stripe. Expiry, reset, changed catalogue, unavailable photos, restart or lost local storage gets an honest recovery message, never a fabricated success or an order in another workspace. For this gateway-only slice, successful return also preserves the bag and has no commerce-ledger effect; state that explicitly in the confirmation.

## The issues that need real work

### Pictures leave the current local-only boundary

`PhotoController` creates browser object URLs, and `BrowserPhotoCache` stores bounded photos in IndexedDB. Those browser-local URLs are unsuitable for a separate Stripe-hosted page. The required path is temporary HTTPS delivery of validated derivatives of the visitor's own selected photos, reachable without our private app cookies. This is an integration requirement inferred from URL-based external rendering, not a claim that the current photos are already hosted. Existing deployed sample URLs may be reused as an optimization only.

Supporting visitor uploads needs a deliberate data-sharing disclosure and a bounded asset-serving/storage design. Send only selected validated derivatives, never originals or arbitrary caller-selected remote URLs. Define byte/count/retention limits, deletion after expiry and behavior when an image is unavailable; reset cannot recall Stripe's already received data. Do not expose private origins, weaken the origin seal, or silently substitute another garment's picture. Local return URLs are supported by Stripe's development example, but local browser photos still need a reachable image source. [Local return example](https://docs.stripe.com/payments/accept-a-payment?payment-ui=checkout&ui=stripe-hosted)

Recommended storage proposal: one **private Google Cloud Storage bucket** for temporary checkout images. A signed read URL gives access to a specific object for a limited time without making the bucket public. Link expiry does not delete the object; deletion needs its own cleanup policy. This recommendation is not an instruction to create a bucket. [Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls), [object lifecycle management](https://docs.cloud.google.com/storage/docs/lifecycle)

The required upload path is:

1. At deliberate checkout, read the actual available photo bytes for each selected colour/view from the visitor's workspace. Reuse validated derivatives where suitable; validate the received bytes on the server and produce small bounded checkout copies. Deduplicate repeated views within that attempt. Do not send the whole upload collection.
2. Store those copies under opaque attempt-scoped object names. Bind photo hashes, selected variant IDs and object references to the same bounded checkout attempt. Another visitor's images or old variant selections must never satisfy this binding.
3. Generate read-only links covering the 30-minute Stripe checkout window. Propose at most one hour of link access, capped by workspace expiry; require the full checkout window to fit before launch. Pass these links together with that visitor's edited titles, chosen sizes/colours, quantities and exact quote to Stripe.
4. If any required photo cannot be prepared, stop before creating/redirecting to a Session and offer retry while preserving the bag. No sample-photo fallback or omitted-photo success for an uploaded garment.
5. Clean up copies after their useful lifetime, including abandoned attempts, with explicit handling for failed uploads, cancel and reset. Configure bounded object retention plus cleanup recovery; acknowledge that Stripe may already have fetched a copy. A lifecycle deletion rule is not proof of immediate erasure at link expiry.

Serving temporary images from app memory/disk is a possible prototype alternative, but Cloud Run's file system is instance-local and lost when an instance stops. That makes a bucket the recommended deployed approach for arbitrary uploads rather than relying on the instance that received them. [Cloud Run file-system behavior](https://docs.cloud.google.com/run/docs/container-contract#filesystem)

### A redirect is a full page departure

Current `reviewBag()` produces an ephemeral review; `placeReviewed()` requires that exact object, unchanged revision/witness/currency and a still-valid command. It must not be reused after navigation. A new pending Stripe attempt must restore through the single session controller, with server-owned verification and an opaque reference bound to the returning visitor. Perform verification through an admitted same-origin request after restoration, preserving the existing strict safety-cookie policy.

Stripe's configured Session expiry is **30 minutes to 24 hours**, unlike our two-minute local confirmation. Propose 30 minutes for the separate gateway attempt, never extending the two-hour workspace. Require at least 30 minutes of workspace lifetime before launching. Reset/cancel should request expiration of an open Session, with truthful handling if already completed or unreachable; browser closure cannot guarantee immediate revocation. Stripe provides an explicit expire operation. [Creation/expiry limits](https://docs.stripe.com/api/checkout/sessions/create), [expire operation](https://docs.stripe.com/api/checkout/sessions/expire)

### Money must match the bag exactly

Keep canonical USD commerce rules and the captured USD/EUR display scope. Map the existing THREAD10 discount, delivery and any projection rounding exactly; compare the created/retrieved Stripe currency and total before redirect and confirmation. Do not silently switch to USD or let Stripe independently recalculate the quote. Disable Adaptive Pricing for this flow, because it can choose a different presentment currency/rate. [Adaptive Pricing](https://docs.stripe.com/payments/currencies/localize-prices/adaptive-pricing?payment-ui=stripe-hosted)

The future quote adapter must specify a deterministic cent allocation and Stripe discount representation, then prove line/component/total parity, including multi-quantity discounts and EUR residuals. Fail with a recoverable review message if a quote cannot be represented. Do not enable independent Stripe promotion entry, automatic tax, adjustable quantities or shipping choices in the first slice. This research has not executed or proved that adapter.

### Key readiness is not an integration test

Use the reported `STRIPE_API_KEY` only in the backend's normal app-local environment loading. Prefer a restricted sandbox key with the exact permissions needed for creating/retrieving/expiring Sessions and chosen inline pricing/discount resources; an unrestricted sandbox secret can technically authenticate but has broader access. Reject live credentials/results. The current environment schema does not read this variable, and its location/type/permissions have not been inspected. Missing or invalid configuration must leave the current local demo available, with no silent provider fallback. [Key types and server-only handling](https://docs.stripe.com/keys)

A gateway demonstration needs no automatic fulfilment: server retrieval on return can verify that returning visitor's test payment. It cannot ensure an order is processed when the visitor never returns. Stripe recommends signed webhooks plus idempotent fulfilment for reliable order processing. Adding that later requires durable order authority and a separately designed authenticated ingress; do not exempt a new public route from current guards as a shortcut. [Fulfilment guidance](https://docs.stripe.com/checkout/fulfillment?payment-ui=stripe-hosted)
