## State ownership and failure recovery

The local adapter uses Node24's built-in SQLite to hold **one encrypted blob**, with an exclusive OS lock and synchronous commits. There is no SQL server, ORM or merchant table. It is under ignored `apps/backend/.shopify-local/`; do not commit or inspect decrypted credentials. The OS releases its lock on process exit, and an interrupted uncommitted write rolls back. A second live backend/local cleanup CLI refuses ownership; stop the verified owner normally first. Do not delete the ledger to clear an already-in-use message: it owns unresolved product cleanup records.

The hosted adapter uses a private GCS object at `shopify/v1/ledger.bin` with generation preconditions and SDK retries disabled. Both adapters use authenticated AES-256-GCM with app-bound context. The entire decrypted deployment ledger is capped at2 MiB, with128 session bindings and ten active/unresolved installations; these are stricter total-state bounds than the planning ceiling. Credentials, OAuth state and ownership metadata remain private. The pending OAuth nonce is encrypted and erased before token exchange; its hash prevents replay.

Do not rotate the encryption key/app identity by overwriting values while unresolved sessions exist. Keep the prior key privately available, stop new connections, settle cleanup under the old configuration, verify completion, then perform a separately documented rotation. Missing/corrupt state or the wrong key fails closed. No volatile live fallback or guessed token reuse is supported.

Token exchanges/refreshes claim durable ownership before HTTP and commit new rotating credentials before other work. An uncertain exchange/refresh becomes needs-attention; it is never silently replayed. Same-shop connections from another workspace are refused while the previous session/cleanup remains unresolved. RTL-164 provides reconnect/recovery and cleanup; RTL-165 integrates the complete local flow.

State access admits one active foreground transaction/read and at most eight waiters, each waiting at most five seconds. Only a confirmed conditional-write conflict reruns a synchronous state transform, at most three attempts; unknown writes and provider HTTP are never automatically retried. Refresh commits retained credentials even if the session expires in flight, but dispatch revalidates the original deadline/generation and leaves expired ownership for cleanup.

## Callback privacy and origin protection

All fixed API operations use the existing origin seal and private backend bridge. Interactive POSTs retain exact browser Origin checks and cookie/tab-proof binding. Callback/install GETs use Shopify HMAC, bounded query/timestamp and consumed state. They return clean fixed resume URLs; no code/state/provider error text is forwarded into the visitor page or report.

Only the newly added callback/install paths are excluded from Next's development incoming-request URL log, because that log includes OAuth query values. They instead emit a private, content-free `shopify_callback` event with fixed operation, HTTP code, request reference and source. Existing request/framework/backend logs remain. Production edge/Cloud Run/proxy access logs need a separately verified redaction/exclusion policy for sensitive OAuth query values before hosted native activation; application code cannot retroactively remove an upstream access log. Do not enable full-URL fetch logging or put analytics on these routes.

## Draft products and image staging

Product reads return twenty rows/page and five pages per explicit browse cycle, with safe text, currency and truncation flags. Reads never import merchant products into Retailor. Export and Update use exact USD cents, clothing/photo validation, two explicit Colour/Size options and complete active variants; they set DRAFT and do not infer stock, cost, discounts, shipping, tax or publication. Ten lifetime create intents include removed and uncertain products. A duplicate Export cannot overwrite merchant edits; a reviewed Update can change only the recorded owned draft. Activated products block updates. An image change requires Remove then Export again, and consumes a new lifetime intent.

Selected derivatives pass the existing bounded sanitizer, then `stagedUploadsCreate(resource:PRODUCT_IMAGE)` and `productCreate(media.originalSource)` use Shopify-managed HTTPS staging. No localhost/blob URL, public bucket, file API or separately reusable file is introduced. Uploads receive no Shopify access token. Media processing and exact field read-back must settle before Ready. Unknown creates reconcile the random server handle plus app-owned `$app:retailor_demo`/`session_export` marker; a visible label or caller product ID is insufficient.

Shopify owns unused staged uploads and their expiry; there is no application deletion API for that reservation in this path. Product deletion is documented to preserve media shared with another product. Native staged-image permissions, pinned API schema, resulting Files behavior and deletion/retention remain pending; do not promise physical media erasure or enable a different file permission without evidence. The cleanup service is composed and locally validated; native provider/media acceptance remains pending.

## Cleanup runner and manual recovery

Selected Remove and whole Disconnect/end are durable POST requests, acknowledged after fencing the foreground generation. The worker verifies ledger ID plus app-owned marker before deletion, then verifies absence. Whole-session cleanup deletes all owned products before `appUninstall`; a successful HTTP response alone is insufficient. Unknown uninstall is probed but never blindly repeated. Cleanup intentionally covers owned products later activated outside Retailor; updates to activated products remain blocked. Merchant products and shared media stay outside arbitrary mutation.

The local backend explicitly starts the shared cleanup use case immediately and every minute, and stops/aborts/settles it on normal shutdown. Imports, runtime factories and health/config start no timer or state I/O. To run the same use case independently after building, use `pnpm --filter @retailor/backend shopify:cleanup`. With local SQLite, first stop the verified backend owner normally; the separate CLI refuses a live owner's file. It loads only backend `.env.local`, opens no HTTP listener, logs fixed content-free counts/codes/request references and closes storage. This task does not run it against live credentials.

Production deliberately does not rely on an in-service timer. Prepare a **private Cloud Run Job using the current backend image**, overriding its command to `node` and arguments to `dist/shopify/cleanup-cli.js`. Use the same authorized app identity, encryption secret and private integration ledger bucket. A separately authorized Scheduler identity invokes that job every minute through the authenticated Cloud Run Jobs API; the job runs under the existing explicitly scoped runtime identity. Grant only the target job invocation and required private bucket/secret access; no public maintenance endpoint, unauthenticated job, frontend secret or origin-guard exception is needed. Exact project/job/identity values, resource creation, IAM and the actual schedule remain pending. Use a55-second application deadline, job timeout longer than that for shutdown, one task/parallelism1 and no platform retry; durable leases reject duplicate invocations. Verify actual scheduler availability and last-run diagnostics before hosted native use.

The durable sweep lease lasts75 seconds; per-shop/action leases last140 seconds to retain in-flight ownership. Every sweep admits at most40 provider calls, ten installations and55 seconds of work. Interactive work has one slot; a second deployment slot remains available for maintenance. Cleanup has its own120-calls/shop/hour allowance, independent of visitor polling/writes. Eight attempts/item use bounded backoff (1m,2m,5m,15m,1h,4h,12h,24h); bounded Retry-After can extend that delay. No sleeping request or export retry queue is added. First-attempt target is within two minutes while the runner, storage and provider are available; in-flight settlement/provider failures can delay completion. Native writes require a private sweep heartbeat within two minutes. That is operational availability, not evidence of native or hosted acceptance.

Credentials are erased after verified cleanup/uninstall. At24 hours after recorded end, maintenance admission refuses further provider work and discards any late refresh result; the next successful sweep erases persisted credentials. Storage/runner outages can delay physical deletion, so continuous scheduling/storage availability and actual cutoff evidence remain required. This is an enforced use deadline, not a claim that an offline machine erases bytes on time. Unresolved private product IDs/markers/manual metadata remain at most seven days after end, or earlier applicable redaction. At cutoff, automatic recovery ends even if Shopify products remain; this cannot prove provider erasure. Missing keys/storage fail closed and never select volatile live state. Preserve known product IDs/handles privately, inspect those exact Retailor demo products in Shopify admin, remove only the known owned entries, then uninstall manually if access was revoked. Do not delete the ledger, change its app/key, adopt matching tags or release an unresolved shop to another workspace to force success.

While the original workspace/proof remains unexpired, verified reauthorization can restore retained **cleanup-only** access after revocation. It keeps the original deadline/ownership/attempt budgets and enables no new export for an ended session. After local reset/expiry removes that proof, use the bounded manual/operator recovery path; do not pass old capabilities through a report or a new guest workspace. An unknown uninstall is not eligible for automatic reauthorization/replay.

## Signed webhooks and privacy

Register exactly `app/uninstalled`, `customers/data_request`, `customers/redact` and `shop/redact`, API version2026-10, at `<FRONTEND_ORIGIN>/api/retailor/v1/shopify/webhook`. Actual subscription/HTTPS delivery is still pending. The public entry retains the server-only origin seal; only this fixed signed protocol omits the browser-Origin requirement. Its private bridge supplies backend Origin/IAM, preserves bounded raw bytes and forwards only three Shopify protocol headers, never a visitor cookie/tab proof. The backend verifies HMAC before parsing and returns401 for an invalid signature. Direct backend browserless access remains denied by Origin/IAM.

Topic-specific verified body shop/domain/ID bind the delivery; arbitrary headers cannot choose a different shop or transform a customer payload into shop redaction. No customer/order records or webhook payloads are retained. Only256 bounded delivery hashes (topic+delivery ID, no body hash) are stored for seven days; a full bound refuses further admission rather than evicting active records. Webhook acknowledgement performs no refresh/provider call. A current-token probe in maintenance reconciles uninstall/redaction notices, with notice-version fencing so an older probe cannot discard a newer delivery. A valid current connection survives an old uninstall/redaction; confirmed revoked access leaves honest manual cleanup or applies redaction. An own-uninstall confirmation preserves verified Cleaned state.

See Shopify's [uninstall contract](https://shopify.dev/docs/api/admin-graphql/latest/mutations/appUninstall), [raw HMAC/delivery guidance](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries) and [privacy webhook reference](https://shopify.dev/docs/apps/build/compliance/privacy-law-compliance).
