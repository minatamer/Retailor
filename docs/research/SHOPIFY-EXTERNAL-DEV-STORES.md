# Shopify: unrelated development-store connections

Research date: **11 November 2026**. RTL-174 supersedes the RTL-168 organization-bound preview entry. Retailor is a standalone web app. The target is a visitor connecting an actual Shopify **dev store** to a temporary Retailor frontend demo, without pasting keys. The temporary Retailor storefront itself is not a Shopify store.

## Decision and strength of evidence

### Owner configuration and audience clarification, 11 November

The owner's screenshot now shows active released version `retailor-2`: embedding off, `read_products,write_products`, `use_legacy_install_flow:false`, App URL `http://127.0.0.1:4310/api/retailor/v1/shopify/install`, callback `http://127.0.0.1:4310/api/retailor/v1/shopify/callback`, webhooks API `2026-10`. The owner separately reports **no distribution selected**, so the current registration is **Undecided**, not a confirmed Public draft or Custom app. This is supplied screenshot/report evidence, not direct authenticated agent inspection.

- Client ID `31874998d05aff3f0b7463e109913066` identifies the **Retailor app**, not the owner's personal account or Retailor Test. Eligible visitors use this same app identity, sign in with their own Shopify account and approve per-store access. No visitor app or visitor API keys are needed. [Official credentials](https://shopify.dev/docs/apps/build/authentication-authorization/manage-credentials) and [authentication](https://shopify.dev/docs/apps/build/authentication-authorization).
- Current source reads `shop.plan.partnerDevelopment` and refuses a false value in the callback. It does not compare the visitor with the owner's Partner organization. Visitors need access to an eligible dev store and installation permission. Creating a dev store requires a Partner account or merchant developer permissions; invited staff can instead access an existing dev store. Third-party installation also requires the user's or organization owner's identity verification. [Dev-store accounts and access](https://shopify.dev/docs/apps/build/stores/development-stores), [installation permissions](https://help.shopify.com/en/manual/apps/install-setup-apps).
- April 9's Shopify staff reproduction explicitly includes **Undecided** managed-install apps and unrelated Partner dev stores. August 27's restrictive answer explicitly addresses **Public drafts**; it does not explicitly settle Undecided behavior. Therefore neither "only the owner can connect" nor "every outside dev store can connect" is established for this registration. Leave distribution Undecided for the next native test; no distribution selection or integration rebuild is needed merely to test it. [April reproduction](https://community.shopify.dev/t/how-can-an-unpublished-shopify-app-be-installed-by-unauthorized-stores/32996), [August public-draft restriction](https://community.shopify.dev/t/draft-apps-on-staging-stores/37242).
- Ordinary live-store access is refused by Retailor's dev-store check. Production configuration still disables Shopify. The current loopback callback reaches the machine running the browser, so a remote visitor cannot use this developer machine through their own `127.0.0.1`.

If an unrelated organization completes consent and the signed callback using this unchanged registration, record that specific success. It establishes actual behavior for that dev-store scenario, not arbitrary live-store access, every store class, future availability or hosted release acceptance. No outside-organization success has yet been observed here. Do not select a permanent distribution type or replace app credentials to resolve this untested hypothesis.

### Original decision and evidence limits

Prepare one shared app with **Undecided distribution** and managed installation as a **local candidate**, not a verified universal solution. Start full-page navigation at `https://admin.shopify.com/oauth/install?client_id=<PUBLIC_CLIENT_ID>`. Remove the organization-bound developer-preview URL. Shopify resolves the visitor's store context; Retailor receives a signed App URL request, verifies it and completes per-store authorization code grant. Retailor independently refuses a non-development shop before making catalogue operations available. No review submission, visitor credentials form, per-visitor app or generic account-discovery API is added. **Production remains unavailable.**

**The requested guaranteed, self-service, no-review external-dev-store flow is not established by this research.** In April, Shopify staff reproduced unrelated-partner installation for undecided/public drafts. On **27 August 2026**, a newer staff answer says public drafts are limited to development stores belonging to their own Partner organization. These conflict; do not cherry-pick April as current policy or assume Undecided avoids the restriction. Custom links are store/Plus-bound. Neither a generic route nor successful OAuth overrides distribution rules.

The April example uses the store-qualified install route. A first-person report supports trying the storeless variant; it reached real Shopify sign-in here, but **authenticated store selection and cross-organization completion remain unverified**. A sign-in page proves routing only. We must observe whether Shopify offers the intended store or reuses the last active store; use its own switcher if necessary. Do not promise a forced chooser or invent query parameters to force one.

Direct authenticated inspection remains pending after the owner chose **“Continue local work first”** at sign-in. The later supplied screenshot/report above now establishes owner-reported configuration, separately from agent inspection and native external-store acceptance. If Shopify rejects the route or omits an external eligible dev store, collect a safe error/reference and confirm the supported entry with Shopify; do not restore a Retailor shop-input form or claim the local test bypasses Shopify's policy.

## Account recipe and native acceptance

Follow [complete owner setup](../operations/SHOPIFY-LOCAL-SETUP.md) for the local candidate. Keep app identity and encryption key unchanged while any existing cleanup remains unresolved. An app already locked to Custom cannot simply be switched to Public; finish existing cleanup under the old registration and plan a separate registration/storage migration explicitly, rather than deleting state or replacing credentials blindly.

Prepared support question (not sent): “For app [Client ID], can unrelated Partner organizations install it on their nontransferable Dev Dashboard dev stores without review, using managed installation and standalone authorization code grant? Does this differ between Undecided and Public/draft? Which Shopify-owned entry supports the visitor choosing a store without entering its domain on our site? April's thread 32996/4 and August's thread 37242/2 appear to disagree.” Use an authenticated support interaction later if native testing does not resolve this. A platform loophole is not a distribution strategy.

Required native evidence, each separately recorded:

1. Actual dashboard distribution and released version: managed install, embedding off, exact local App URL/callback and `write_products`.
2. Owner's store through the **new** CTA, including consent decline, return, reconnection and no automatic products. Prior own-store success used the old entry.
3. A visitor in a genuinely **different partner organization**, with an eligible dev store and Shopify third-party identity requirements satisfied; no collaborator shortcut, pasted app keys or store URL in Retailor. Observe actual store selection and same-tab callback.
4. Confirm non-dev stores do not become usable Retailor connections. Managed installation can have occurred on Shopify before Retailor rejects a shop; disconnect/cleanup must retain authority to uninstall rather than treat this as “nothing happened.”
5. Read/import/export/media/collection/update/remove/disconnect/expiry against real Shopify, preserving existing sentinel products. These product semantics are separate from OAuth success.

The local regression suite injects two distinct shops into the real authenticated service and durable encrypted ledger. That proves Retailor isolation and lack of organization coupling, **not Shopify's platform acceptance**. Hosted callbacks/storage/worker/IAM, current Linux images/scanners and public/paid release remain separate pending work. Local callbacks point to the machine running Retailor; another person's browser cannot reach this machine through their own `127.0.0.1`. Testing on another machine requires running Retailor there with securely provisioned owner app configuration, or a separately authorized hosted setup later.
